# v1.1 Cloud Sync

v1.1 starts the online foundation without changing the live v1.0 App Store build.

## Scope

- Keep the game playable as guest.
- Send completed game summaries to Supabase only when the user has a session.
- Persist authenticated game results in a local write-ahead queue before sending.
- Retry queued results on app launch, sign-in, foreground activation, and the next completed game.
- Remove only the successfully accepted result from the queue; server-side `client_result_id` uniqueness keeps retries idempotent.
- Keep server-owned totals in Postgres through `submit_game_result(p_result jsonb)`.
- Restore account totals, streak days, weekly progress, and achievements from Supabase at sign-in.
- Keep guest progress and each signed-in user's local snapshot in separate storage keys.
- Let signed-in players choose one unique username and an optional display name.
- Let players search safe public profile fields, send friend requests, and manage
  accepted friendships.
- Show the signed-in player and accepted friends in a private weekly score board.
- Show a safe aggregate profile card only for accepted friends.
- Show the signed-in player an in-app count of pending incoming friend requests.
- Show private in-app notifications for new friend requests and accepted requests.
- Let signed-in players explicitly enable remote friend notifications from Settings.
- Deliver remote notifications through Expo Push Service and Apple Push Notification
  service without exposing device tokens to clients.
- Show recent completed-game summaries from accepted friends.
- Let signed-in users permanently delete their account and cloud data in the app.
- Keep v1.1 cloud work isolated on the `v1.1-cloud-sync` branch until it is
  ready for a separate TestFlight build.

## Client Payload

The app sends one summary at the end of a completed game:

- `client_result_id`
- `mode`
- `difficulty`
- `score`
- `awarded_score`
- `targets_solved`
- `target_count`
- `operation_count`
- `duration_seconds`
- `hint_used_count`
- `puzzle_key`
- `completed`
- `par`
- `board_size`
- `source_numbers`
- `target_values`
- `locale`
- `client_finished_at`
- `client_utc_offset_minutes`

The client does not directly update totals, streaks, weekly scores, or achievements.

The local queue keeps at most 50 recent results per account and 100 results on the
device. Raw queued results expire after 90 days, matching the server event retention
window. Queue reads and writes are serialized so a foreground retry cannot overwrite
a game that finishes at the same time.

Supabase is authoritative for account totals, streaks, achievements, daily progress,
and the current weekly score whenever that account has no queued game results. If
the account still has offline results waiting to be sent, the app temporarily keeps
the higher local snapshot and retries later. A successful foreground or post-game
sync reloads the cloud snapshot and removes stale local-only values.

## Player Profiles

The account panel reads the signed-in user's private `profiles` row. Usernames are
normalized to lowercase and accept 3-24 ASCII letters, numbers, or underscores.
Display names are optional and accept up to 40 characters, including localized
characters.

Authenticated clients cannot update the `profiles` table directly. Profile changes
go through `update_own_profile`, which derives the user id from the current session,
normalizes the submitted values, and enforces username uniqueness in Postgres.

## Friend Connections

The friends panel requires a signed-in account with a username. Player search returns
only the user id, username, display name, and the relationship state for the signed-in
player. Email addresses and private profile rows are never returned by search.

Friend requests and accepted friendships are stored as one canonical relationship per
player pair. Clients cannot read or write the underlying tables directly. All actions
go through authenticated security-definer functions that derive the current player
from `auth.uid()`, validate ownership, and expose only relationships involving that
player.

Weekly and monthly aggregate rows are private to their owner. The friends-only weekly
board is returned by `list_friend_weekly_leaderboard`, which exposes the current
player and accepted friends for one validated week key. Removing a friendship removes
that player from future board reads without deleting either player's score history.

Accepted friends can open a summary card backed by `get_friend_profile`. It contains
only username, display name, total score, best score, completed game count, best
streak, and the current weekly score. Non-friends cannot call this function for
another player, and no email address or raw game event is returned.

The pending request badge is backed by `get_incoming_friend_request_count` and is
refreshed after friend actions, sign-in, and foreground activation.

Friend requests and accepted requests also create private rows in
`user_notifications`. The client cannot read or write this table directly. It uses
authenticated RPCs to list safe actor labels, read the unread count, mark visible
notifications as read, and dismiss its own notifications. Another account cannot
read, mark, or delete those rows. Notifications expire after 30 days and the
`cleanup-expired-user-notifications` cron job removes expired rows daily at 03:29
UTC.

Remote friend notifications are opt-in. The app asks for the operating-system
permission only after the signed-in player enables notifications in Settings. It
stores the resulting Expo push token through `register_push_device`; clients cannot
read `push_devices` or `push_deliveries` directly. One active token cannot be claimed
by another account, and one account can keep at most five active devices.

The app detaches its stored token before signing out so notifications for the old
account cannot reach the next account using that installation. Revoked permissions
and Expo `DeviceNotRegistered` receipts disable the affected token. Deleting an
account removes its devices through foreign-key cascades.

The `push-worker` Edge Function is called every minute by Supabase Cron with a
random worker secret stored in Vault. It claims pending rows with
`FOR UPDATE SKIP LOCKED`, sends at most 100 device messages per run, and checks Expo
delivery receipts after 15 minutes. Failed work is retried at most three times.
Delivery diagnostics are retained for 30 days and then removed by a daily cleanup
job. Notification rows still expire after 30 days.

The worker endpoint rejects requests without the Vault-backed secret, uses the
service role only inside the Edge Function, and never logs tokens or secrets. Expo's
optional enhanced push security access token can be added later as an Edge Function
secret named `EXPO_ACCESS_TOKEN`.

The friend activity section is backed by `list_friend_activity`. It returns at most
20 completed games from accepted friends during the last 30 days. The response is
limited to public profile labels plus mode, difficulty, awarded score, solved target
counts, duration, and play time. Puzzle contents, email addresses, client result ids,
and raw payloads remain private. Removing a friendship immediately removes that
player's events from future activity reads.

Challenge results are archived separately from the 24-hour race rooms. Each player
receives a mirrored summary containing only the opponent's public profile label,
outcome, scores, move counts, durations, target count, and completion time. Raw
operation history, puzzle values, room codes, email addresses, and authentication
data are not copied into history. `list_challenge_history` returns only the signed-in
player's latest entries, and the archive is capped at 100 summaries per player.
Closing or expiring a completed room does not remove its summary; deleting either
account removes related summaries through foreign-key cascades.

## Required Environment

Create a local `.env` file from `.env.example`:

```text
EXPO_PUBLIC_SUPABASE_URL=https://xuggavmtqgsxazbccfxj.supabase.co
EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY=...
EXPO_PUBLIC_AUTH_REDIRECT_URL=islem://auth/callback
EXPO_PUBLIC_TURNSTILE_SITE_KEY=...
EXPO_PUBLIC_TURNSTILE_URL=https://aerkut-ops.github.io/islem-mobile/turnstile.html
```

The Turnstile site key is public and is included in the app build. The Turnstile secret belongs only in Supabase Auth settings. Never commit `.env`, Turnstile secrets, service role keys, database passwords, Apple keys, or EAS secrets.

The Expo project id is public app configuration. The Apple APNs key is managed by
EAS Credentials and must never be downloaded into or committed to this repository.

Add `islem://**` to Supabase Auth redirect URLs before testing email magic links.
For the separately installed local device build, use `islem-dev://auth/callback` and add `islem-dev://**` to the same allowlist.

After applying the migration, verify that the `cleanup-expired-score-events` job is active under Integrations > Cron > Jobs. It runs daily at 03:17 UTC and removes only raw game events whose 90-day retention period has ended. Permanent player statistics, daily progress, weekly/monthly summaries, and achievement unlocks remain intact.

## Account Deletion

Deploy the authenticated Edge Function after linking the project:

```text
npx supabase functions deploy delete-account --project-ref xuggavmtqgsxazbccfxj --use-api
```

The function requires a valid user JWT and an explicit confirmation value. It deletes the authenticated `auth.users` row through the server-side admin client; foreign-key cascades remove the related profile, scores, streak, achievements, and game summaries. Never expose a Supabase secret key in the app.

## Email Delivery

Custom SMTP is enabled for the v1.1 beta account flow. A magic link requested from the installed iOS app was delivered through Gmail SMTP, opened the `islem-dev://auth/callback` route, signed in the development test account, and remained signed in after the app was fully closed and reopened.

The Gmail sender is suitable for limited beta testing only. Replace it with a transactional email provider and a verified sending domain before increasing authentication email limits or onboarding users at scale. Keep SMTP passwords and provider API keys outside the repository.

The bilingual magic-link email source is versioned at `supabase/templates/magic-link.html`. Keep the hosted Supabase Auth subject and template synchronized with this file when the copy or design changes.

## Bot and Abuse Protection

Email-link and password sign-in can be protected with Cloudflare Turnstile. The native app opens the HTTPS challenge page at `store-web/turnstile.html` in a constrained WebView, receives a single-use token, and passes that token to Supabase Auth with the sign-in request.

Before enabling CAPTCHA in production:

1. Create a managed Turnstile widget in the Cloudflare dashboard.
2. Restrict the widget hostname to `aerkut-ops.github.io`.
3. Put the public site key in the EAS production environment.
4. Select Turnstile under Supabase Authentication > Bot and Abuse Protection and enter the secret key there.
5. Build and test the app before enabling CAPTCHA for all users.

Use Cloudflare's official test keys only during development. Never ship a production build with a test key, and never put the secret key in the app or repository.

When the official always-pass Turnstile site key is present in a development build, the app sends Cloudflare's official dummy token directly to Supabase instead of opening the WebView. This keeps local account testing deterministic while Supabase uses the matching test secret. Release builds never use this shortcut; a real site key opens the hosted WebView challenge and still fails closed after a 20-second timeout.

## Native Build Note

The Turnstile screen uses `react-native-webview` 16, which matches React Native 0.86's new architecture. This version is intentionally excluded from Expo's recommended-version validation in `package.json`.

On iOS, `expo-build-properties` sets `buildReactNativeFromSource` to `true`. The setting avoids native linker incompatibilities between WebView 16 and Expo's prebuilt React Native core. Clean local and simulator builds were verified with this configuration. iOS builds take longer because React Native is compiled from source; do not remove the setting without repeating a clean native build and the complete authentication test.

`expo-notifications` is configured in `app.json`. Production EAS credentials must
include an Apple Push Notifications key for `com.aydin.islem`. Local physical-device
builds also need the Push Notifications capability and an `aps-environment`
entitlement in the generated Xcode project. Generated `ios` files are not committed.

## Security Verification

Run the read-only Row Level Security check before a TestFlight build:

```text
npm run check:cloud
npm run check:profile
npm run check:friends
npm run check:challenges
```

The command first verifies that passwordless email sign-in rejects requests without CAPTCHA verification. It then signs in with both Keychain-backed test accounts and verifies that profiles, player statistics, daily progress, weekly and monthly summaries, raw score events, achievements, notifications, and deletion requests are isolated per user. It also verifies that anonymous requests cannot read those tables.

The profile check assigns stable usernames to the development and App Review
accounts, verifies that profile reads remain private, confirms that direct table
updates and anonymous RPC calls are denied, and checks username uniqueness.

The friend check creates temporary requests only between the two Keychain-backed
test accounts, verifies cancel and decline behavior, accepts a final request, checks
both sides of the friendship, safe friend profiles, activity summaries, request
counts, private request and acceptance notifications, read/dismiss ownership, and
weekly board, confirms that non-friend profiles, activity, and scores, direct table
reads, and anonymous RPC calls are denied, and removes the test relationship and
temporary notifications before it exits.

The friend check also verifies that an active Expo token cannot be moved to another
account, that its owner can disable it, and that another account can register it only
after detachment. Direct and anonymous access to device and delivery tables remains
denied.

The challenge check creates a temporary race between the Keychain-backed accounts,
verifies puzzle agreement, server-side arithmetic, idempotent operation replay,
result calculation, notification cleanup, direct-table isolation, and anonymous RPC
denial. It also verifies that the completed result is mirrored safely for both
players and remains in history after the live room is closed.

When the local environment uses Cloudflare's official always-pass test key, this check sends the matching official dummy token to Supabase. It does not bypass a real production widget: production Turnstile tokens are single-use and cannot be stored in the repository.
